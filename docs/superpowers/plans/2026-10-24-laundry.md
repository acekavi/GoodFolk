# Linen and Guest Laundry — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Track hotel linen by item and location through append-only movements, with par-based low-stock alerts and
counted laundry batches. Take guest laundry orders from a price list and post their charge to the guest folio on
delivery.

**Architecture:**
- **A new module, `modules/laundry`**, depending on `db`, `rooms`, `folio` and `audit` (for ops alerts). It has these
  parts:
  - `linen.rs`: items, locations, par;
  - `stock.rs`: movements, stock, low stock;
  - `batches.rs`;
  - `prices.rs`;
  - `orders.rs`, where delivery posts through `folio::post_for_stay`.
- **core-api** adds the REST routes, GraphQL fields, permissions, events and the review's laundry lines.
- **The SPA** adds the Linen page, the Guest laundry board, the order form in the reservation modal, the price list
  settings, and the alert banner.

**Tech Stack:** Rust 1.99, axum 0.8, sqlx 0.9, async-graphql 7.2, PostgreSQL 17 (forced RLS), SvelteKit 2 / Svelte 5,
TanStack Query, Playwright, Bun.

**Spec:** [docs/specs/laundry.md](../../specs/laundry.md). It is the authority: read the sections a task names.

**Execution method (the owner's standing preference):** each task is implemented once on branch `phase-laundry`, then
reviewed, with fix rounds. A final whole-branch review and one fix wave follow, then a manual testing guide.

- **Money:** prices are in the property's base currency, net of tax, in minor units. Taxes come from the folio's tax

## Review Focus

- **Stock never drifts from its movements, even under concurrency.** Two people moving the same item between the same
  two locations in opposite directions must neither deadlock nor lose a count. Test: Task 3.
- **A batch received short is not forgotten.** The shortfall stays visible at the laundry until it is returned or
  written off, and receiving more than is outstanding is refused. Test: Task 4.
- **Delivery charges exactly once.** A double-click, a replayed request, or a refused posting followed by a retry posts
  each line once, and a refused posting leaves the order `ready`. Test: Task 6.
- **Prices taken are prices charged.** Changing or deactivating a price after an order is taken does not change what
  the order charges. Test: Task 6.
- **Who sees what.** Housekeeping can move linen but cannot write off or change par. Front desk can take orders but
  cannot see linen. The `linen` alert is shown only to `LinenManage` holders. Test: Task 7.

### Task 3: Movements, stock and low stock

**Files:** create `modules/laundry/src/stock.rs`. Test: `modules/laundry/tests/stock.rs`.

**Interfaces (exact):**
```rust
pub enum MovementKind { Receive, Transfer, Send, Return, WriteOff }
pub struct NewMovement { pub item_id: Uuid, pub kind: MovementKind, pub quantity: i32,
    pub from_location_id: Option<Uuid>, pub to_location_id: Option<Uuid>, pub reason: Option<String> }
pub struct Movement { pub id: Uuid, pub item_id: Uuid, pub kind: MovementKind, pub quantity: i32,
    pub from_location_id: Option<Uuid>, pub to_location_id: Option<Uuid>, pub batch_id: Option<Uuid>,
    pub reason: Option<String>, pub business_date: Date, pub moved_by: Option<Uuid>, pub moved_at: OffsetDateTime }
/// receive, transfer or write_off (send/return only through batches: Invalid otherwise).
pub async fn record(tx, tenant, actor: UserId, property, movement: NewMovement) -> Result<Movement, LaundryError>;
/// Shared with batches: applies movements in one transaction (stock rows locked first, ascending (location, item)),
/// then re-checks low stock for the touched locations.
pub(crate) async fn apply(tx, tenant, actor, property, batch: Option<Uuid>, movements: &[NewMovement]) -> Result<Vec<Movement>, LaundryError>;
pub struct StockCell { pub location_id: Uuid, pub item_id: Uuid, pub quantity: i32, pub par: Option<i32>, pub low: bool }
pub async fn stock(tx, property) -> Result<Vec<StockCell>, LaundryError>;     // every active location × active item
pub async fn movements(tx, property, first: u32, after: Option<Uuid>, location: Option<Uuid>) -> Result<Vec<Movement>, LaundryError>;
```

**Rules:**
- **Kind matches locations:**
  - `receive` and `transfer` end at a store or pantry; `transfer` starts at one too;
  - `send` ends at a laundry or vendor location, and `return` starts at one;
  - `write_off` may start anywhere and needs a reason;
  - locations and the item must be active and of the property.
- **The order of a movement's work:**
  1. Lock the stock rows of the involved `(location, item)` pairs in ascending order (`insert … on conflict do
     nothing`, then `select … for update` in order).
  2. Check that the source has the quantity (`409` "Only <n> <code> at <location>").
  3. Update, then insert the movement with the business date (`for share`).
  4. Audit `linen_movement.recorded`.
  5. Re-check low stock.
  6. Notify `linen_key`.
- **Par totals:**
  - a pantry: Σ over active rooms whose `section_id` is the pantry's section of `linen_par.quantity` for the room's
    type and item;
  - the store: the same over active rooms in no active pantry's section.
  - A cell is low when it has a par and the quantity is below it.
- **The alert:** after `apply`, compute the low cells of the property (all of them, so the alert's text is complete).
  If any are low, `audit::alerts::raise(Linen, "<location>: <code> <qty> of <par>; …")`, at most 2000 characters,
  ending in "…" when cut. Otherwise `clear(Linen)`.

- [ ] **Tests:**
  - receive, transfer and write-off update stock;
  - a below-zero transfer is refused with the message, and nothing changes;
  - a kind/location mismatch is `Invalid`;
  - a write-off without a reason is `Invalid`;
  - **property test** (seeded `StdRng`, 200 random movements across 3 locations and 2 items, including ones that must be
    refused): after each step, every stock cell equals `Σ to − Σ from` over `linen_movement`;
  - **low stock:** a pantry's par equals Σ over its section's rooms, and the store's par covers the rest. The alert is
    raised when a cell drops below par and cleared when it is back;
  - 20 rounds of two concurrent opposite transfers between the same locations finish with no deadlock and the right
    totals (`tokio::join!` with a 10 s timeout per round).
- [ ] Commit with the message `feat(laundry): linen movements, stock and low-stock alerts`.

### Task 4: Laundry batches

**Files:** create `modules/laundry/src/batches.rs`. Test: `modules/laundry/tests/batches.rs`.

**Interfaces (exact):**
```rust
pub struct BatchLine { pub item_id: Uuid, pub sent: i32, pub returned: i32, pub written_off: i32 }  // outstanding = sent - returned - written_off
pub struct Batch { pub id: Uuid, pub from_location_id: Uuid, pub to_location_id: Uuid, pub status: BatchStatus,
    pub note: Option<String>, pub sent_by: Option<Uuid>, pub sent_at: OffsetDateTime, pub received_by: Option<Uuid>,
    pub received_at: Option<OffsetDateTime>, pub version: i32, pub lines: Vec<BatchLine> }
impl Batch { pub fn outstanding(&self) -> i32; pub fn settled(&self) -> bool; }   // settled: received and outstanding 0
pub async fn send(tx, tenant, actor, property, from: Uuid, to: Uuid, counts: &[(Uuid, i32)], note: Option<String>) -> Result<Batch, LaundryError>;   // 1–200 items, distinct
pub async fn receive(tx, tenant, actor, property, batch: Uuid, expected_version: i32, back_to: Option<Uuid>, counts: &[(Uuid, i32)]) -> Result<Batch, LaundryError>;
pub enum Settle { Return { back_to: Option<Uuid>, counts: Vec<(Uuid, i32)> }, WriteOff { reason: String, counts: Vec<(Uuid, i32)> } }
pub async fn settle(tx, tenant, actor, property, batch: Uuid, expected_version: i32, settle: Settle) -> Result<Batch, LaundryError>;
pub async fn list_batches(tx, property, status: Option<BatchStatus>) -> Result<Vec<Batch>, LaundryError>;  // newest first, ≤ 200
```

**Rules:**
- **Sending:** a store or pantry to a laundry or vendor location; uses `stock::apply` with `send` movements carrying
  the batch.
- **Receiving:**
  - only from `sent`;
  - counts are per item of the batch, 0 ≤ count ≤ outstanding (`Invalid` "Only <n> <code> are still out");
  - items left out of `counts` count as 0;
  - `return` movements go to `back_to` (default the batch's `from`), which must be a store or pantry;
  - the batch becomes `received`;
  - audit `laundry_batch.received` with `{per item: sent, received, difference}`.
- **Settling:** only `received` batches with something outstanding, with count ≤ outstanding. `WriteOff` creates
  `write_off` movements from the laundry location carrying the batch. Audit `laundry_batch.settled`.
- **Version and events:** every change bumps `version` and notifies `linen_key`.

- [ ] **Tests:**
  - send 20 sheets and 30 towels: the store goes down and the laundry goes up;
  - receive 18 and 30: the batch is `received` with a difference of 2 sheets, which are still in the laundry's stock;
  - a later return of 1, then a write-off of 1 with a reason: the batch is settled;
  - receiving more than outstanding is refused;
  - receiving twice is refused;
  - settling an unreceived batch is refused;
  - a stale version is `VersionMismatch`;
  - sending more than the store holds is refused, and nothing changes.
- [ ] Commit with the message `feat(laundry): batches sent and received with their differences`.

**Interfaces (exact):**
```rust
pub enum OrderStatus { Collected, Processing, Ready, Delivered, Cancelled }
pub struct OrderLine { pub position: i32, pub price_id: Uuid, pub item_code: String, pub service: Service, pub name: String, pub unit_price: i64, pub quantity: i32 }
pub struct Order { pub id: Uuid, pub reservation_room_id: Uuid, pub room_number: String, pub guest: String,
    pub status: OrderStatus, pub note: Option<String>, pub lines: Vec<OrderLine>, pub total: i64, pub currency: String,
    pub created_at: OffsetDateTime, pub status_at: OffsetDateTime, pub delivered_at: Option<OffsetDateTime>, pub version: i32 }
pub async fn create_order(tx, tenant, actor, property, reservation_room: Uuid, lines: &[(Uuid, i32)], note: Option<String>) -> Result<Order, LaundryError>;
pub async fn update_lines(tx, tenant, actor, property, id, expected_version, lines: &[(Uuid, i32)], note: Option<Option<String>>) -> Result<Order, LaundryError>;
/// `to` is the next status or Cancelled. Delivery posts the charge.
pub async fn set_status(tx, tenant, actor, property, id, expected_version, to: OrderStatus) -> Result<Order, LaundryError>;
pub async fn list_orders(tx, property, status: Option<OrderStatus>) -> Result<Vec<Order>, LaundryError>;   // open first, ≤ 500
pub async fn orders_for_stay(tx, property, reservation_room: Uuid) -> Result<Vec<Order>, LaundryError>;
```

**Rules:**
- **Creating:** the stay is checked in at the property (`Invalid` "Laundry is taken for an in-house stay"). There are
  1–50 lines, each with an active price of the property and a quantity of 1–100, and price ids may repeat. Lines copy
  the price's code, service, name and price. The room number is the stay's current room. Audit
  `laundry_order.created`.
- **Lines:** they are replaced (delete, then insert) only while `collected`.
- **Status:** moves exactly one step (`collected → processing → ready → delivered`), or to `cancelled` from any step
  before `delivered`. Anything else is a `409` naming both statuses.
- **Delivery:**
  1. Lock the order `for update`.
  2. Require the stay still checked in (`409` "The guest has checked out; post the charge on their folio").
  3. For each line in position order, call `folio::post_for_stay(tx, tenant, Some(actor), stay, NewCharge { source:
     Laundry, category: "laundry", description: "Laundry: <name> × <qty>", quantity: qty, unit_net: unit_price,
     currency: base, business_date: today (for share), posting_key: Some("laundry:<order>:<position>"), inclusive:
     false })`.
  4. Set `delivered`.
  - Any folio refusal propagates as `LaundryError::Folio`, so the transaction rolls back and the order stays `ready`.
- **Audit and events:** every change audits `laundry_order.status_changed {from, to}` and notifies `laundry_key`. A
  delivery also notifies the folio keys `post_for_stay` returns, or reads them from the lines.
- **The review:** the posted-lines query's source filter becomes `('manual', 'cancellation_fee', 'no_show_fee',
  'laundry')`.

- [ ] **Tests:**

  - delivering a cancelled or already delivered order is refused;
  - **delivery:**

    - routing a reservation's `laundry` category to an account sends the lines there;
    - posting the same key again adds nothing;
  - a delivery on an invoiced guest folio is refused and the order stays `ready`;
