# Phase 4 Tape Chart Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A front-desk tape chart. It shows 10 rooms per page with a room picker. New bookings get a room
automatically. Drag and drop is backed by the Phase 3 commands. Live updates arrive over the existing
server-sent-events stream. Every interaction has a measured speed gate.

**Architecture:**
- Server: two new GraphQL reads, `tapeWindow` and `unassignedStays`, run as indexed range scans over at most 10
  rooms. A new `tape:<property>:<YYYY-MM>` event key is emitted by every command that changes what the chart
  shows. `create_reservation` and a type-changing `modify_room` auto-assign the tightest-fitting free room under
  `FOR UPDATE SKIP LOCKED`.
- Client: a new `/p/[property]/tape` route renders 14-day tiles (fixed Monday epoch). It has sticky rail and header,
  a CSS-gradient day grid and absolutely positioned bars. It keeps an LRU of tiles keyed by the page's room ids.
  Room filtering and paging happen entirely in the browser.
- GraphQL gets a production persisted-query allowlist generated by codegen.

**Tech Stack:** Rust 1.97 (edition 2024), axum 0.8, sqlx 0.9, async-graphql 7.2, PostgreSQL 17 with forced RLS,
SvelteKit 2 / Svelte 5, TanStack Query (svelte-query), GraphQL Codegen client preset, Playwright, Bun.

**Spec:** [docs/specs/phase-4-tape-chart.md](../../specs/phase-4-tape-chart.md). Read it before any task. It is the
authority; this plan argues from it.

**Execution method (the owner's standing preference):** there is no separate "verify then rebuild" pass. Each task
is implemented once, on branch `phase-4-tape-chart`, by one implementer. A task reviewer then checks it against
this plan and the spec, with fix rounds, followed by a final whole-branch review and one fix wave. The code blocks
below are exact for the load-bearing parts (SQL, algorithms, keys, public signatures, tests that pin behaviour).
Elsewhere, implementers write code that matches the surrounding module's patterns, and reviewers hold them to it.

## Global Constraints

- Postgres runs locally without Docker on port 5432. Tests run as
  `DATABASE_URL=postgres://goodfolk_owner:goodfolk_owner_dev@localhost:5432/goodfolk cargo test …`.
- The e2e DB is `goodfolk_e2e_p4`. The controller creates it and migrates it through 0010. Never drop any database.
- Every Rust task ends green on all three:
  - `cargo test --workspace`;
  - `cargo fmt --all --check`;
  - `cargo clippy --workspace --all-targets -- -D warnings`.
- Every web task ends green on `bun run lint && bun run check && bun run test && bun run build`. Use Bun only, never
  npm, npx, yarn or pnpm. Tasks that touch UI or e2e also pass the default `bun run test:e2e`.
- After any API change, run `bun run api:schemas && bun run codegen` in web/pms and commit the generated files.
- Commit messages are exact as given. Add no body and no trailer. No AI attribution anywhere.
- Lock order (docs/design/api-conventions.md): `reservation_room` → `room` → `room_block` → `inventory_day`, and
  `reservation` last. Auto-assignment takes candidate `room` rows only with `FOR UPDATE SKIP LOCKED`, so it never
  waits on a room lock.
- `tapeWindow`:
  - at most 10 room ids (`MAX_TAPE_ROOMS = 10`), all belonging to the property;
  - a window of at most 42 days (`MAX_TAPE_DAYS = 42`).
- Tiles are 14 days long, anchored at 2020-01-06 (a Monday). The client keeps an LRU of 12 tiles and prefetches one
  tile ahead in the scroll direction.
- The event key is `tape:<property>:<YYYY-MM>`, emitted for every month the old and new ranges touch.
- Permissions:
  - reads need `ReservationsView`;
  - drags, Assign… and Move… need `ReservationsManage`;
  - without `ReservationsManage` the chart is read-only.
- Tightest fit looks at most 60 days either way (`FIT_HORIZON_DAYS = 60`). Ties go to the first room in rail order
  (`rt.sort_order, r.sort_order, r.number`).
- Performance gates (500 rooms, 18 months of bookings at 80% occupancy):

  | Gate | Limit |
  |---|---|
  | `tapeWindow` p95 | < 5 ms |
  | `unassignedStays` p95 | < 5 ms |
  | page or picker change | < 50 ms |
  | horizontal scroll | ≥ 58 fps median, no long task > 50 ms |
  | first open | < 400 ms |
  | drag ghost | within one frame |
  | DOM nodes | < 3,000 |
  | compressed `tapeWindow` payload | < 8 KB |

  Never raise a threshold. Only the owner can.
- Live updates use the existing SSE stream. No WebSockets.

## Review Focus

These are failure modes no task's tests would otherwise exercise. Each has a test added in the task named.
- **A multi-room booking of one type.** Every room must get a distinct room, or be left unassigned; never the same
  room twice. Test: Task 3.
- **Needs-a-room reasons.** A stay whose nights start before the business date (a past arrival that's still
  unassigned) must not error and must not be misreported as "overbooked", because it has no counter rows. Test:
  Task 5.
- **Range chips.** A range chip with its bounds reversed (`120-101`) or with non-numeric rooms (`A1`–`A9`) must behave
  predictably. Reversed means the same range. Non-numeric numbers compare naturally. Test: Task 8.
- **A stale page.** A page shown after rooms are deactivated or the picker narrows below the current page must clamp
  to the last page, not show an empty chart. Test: Task 8.
- **Undo after someone else moved the stay.** Undo must refuse with the 412 message and not overwrite. Test: Task 11.

**Algorithm (exact).** The ranking query takes no locks:

```sql
with candidate as (
  select r.id, r.number, rt.sort_order as type_order, r.sort_order as room_order,
         coalesce((select $3 - max(upper(x.range)) from (
                      select a.stay as range from reservation_room a
                      where a.room_id = r.id and a.status not in ('cancelled', 'no_show')
                        and a.stay && daterange($3 - $5, $3)
                      union all
                      select b.period from room_block b
                      where b.room_id = r.id and b.released_at is null and b.period && daterange($3 - $5, $3)
                   ) x), $5) as gap_before,
         coalesce((select min(lower(x.range)) - $4 from (
                      select a.stay as range from reservation_room a
                      where a.room_id = r.id and a.status not in ('cancelled', 'no_show')
                        and a.stay && daterange($4, $4 + $5)
                      union all
                      select b.period from room_block b
                      where b.room_id = r.id and b.released_at is null and b.period && daterange($4, $4 + $5)
                   ) x), $5) as gap_after
  from room r join room_type rt on rt.id = r.room_type_id
  where r.property_id = $1 and r.room_type_id = $2 and r.active
    and not exists (select 1 from reservation_room a
                    where a.room_id = r.id and a.status not in ('cancelled', 'no_show')
                      and a.stay && daterange($3, $4))
    and not exists (select 1 from room_block b
                    where b.room_id = r.id and b.released_at is null and b.period && daterange($3, $4))
)
select id, number from candidate
order by greatest(gap_before, 0) + greatest(gap_after, 0), type_order, room_order, number
```

(`$1` property, `$2` room type, `$3` check_in, `$4` check_out, `$5` `FIT_HORIZON_DAYS` as an integer; date − date is
an integer in Postgres.)

Then, for each candidate in order:
1. Run `select 1 from room where id = $1 for update skip locked`. If no row comes back, skip the candidate.
2. Re-run both `not exists` checks for that room. A stay or block committed between the ranking and the lock is
   seen now, because read committed takes a fresh snapshot per statement. If either finds a row, skip the
   candidate; its lock is released at commit.
3. Return the first room that passes.

The rooms skipped in step 2 stay locked until commit. That's harmless, but record it in the doc comment.

**Wiring into create_reservation.** Inside the existing per-room insert loop, which runs after the
`property_counter` row is taken, call `pick_room` for each booked room in input order, and insert its
`reservation_room` with `room_id` set to the result. The lock order becomes `inventory_day` → `property_counter` →
`room`. The `room` locks are SKIP LOCKED, so they never wait, and nothing that holds a `room` lock waits on
`property_counter`, so no cycle can form.

Pick and insert room by room: a room of the same type picked earlier in this transaction is then already inserted,
and the next pick's `not exists` excludes it. The confirmation-number rule ("taken only after every refusal check")
still holds, because picking never refuses.

The exclusion constraint stays the final guard. If the insert still hits `reservation_room_no_double_booking`, which
should be impossible under the room lock, surface it as an internal error. Don't retry.

**Rules:**
- **`tape_window` refuses (Invalid):**
  - `to <= from`, or `to - from > 42`;
  - more than 10 rooms, or an empty list;
  - any room id not an active or inactive room of the property: check `count(*) where id = any($rooms) and
    property_id = $1` equals the number of distinct ids.
- **`tape_window` returns:**
  - Stays: `room_id = any($rooms) and status not in ('cancelled', 'no_show') and stay && daterange($from, $to)`,

    `block_reason.label`.
  - Guest names are formatted in SQL: `g.last_name || ', ' || left(g.first_name, 1) || '.'`. When `first_name` is
    empty, the last name alone.
- **`unassigned_stays`:**
  - Selects `property_id = $1 and room_id is null and status = 'confirmed' and stay && daterange($2, $3)`, the
    partial index's exact predicate.
  - It limits to 42 days like `tape_window`.
  - `reason` is `overbooked` when `exists (select 1 from inventory_day i where i.property_id = $1 and
